## 1. 文档定位与一条总原则

本 harness 的长板是**证据治理与交付合规**（两端），短板是**中间的“做”与“写”的执行交接与真实验证**；而压在所有结论之上的最大事实是：**能力基准从未真跑过**，现有全部证据都是“回归/Schema 正确”，不是“真实赛题能力”。

因此所有建议遵循一条总原则（与仓库自身 `HARNESS_INTEGRATION_ANALYSIS` 的判断一致）：

> **优先把“已经建好的链路真正跑通并验证”，而不是继续堆新的 Gate、新的 Agent、新的 Markdown 或新的 Schema。** 每加一样东西，先问：它的消费者是谁？没有消费者的工具就是“断焊”。

## 2. 总体结论（30 秒版）

1. **架构本身是成熟、纪律性强的。** 三层所有权（执行事实 / 投影 / 控制）、不可绕过=检查时重算、作者面与机器投影分离、preset 的 `SAFE_INVARIANTS` 不可关——这些在同类里是领先的。
2. **与优秀同类相比：** 你独有且更强的是“全阶段机器强制的证据门控 + 赛事合规 + 统一复现链”；同类仍更强的是“模型→代码的操作性协议、求解器鲁棒清单、渲染级图 QA、写作的证据分配纪律、角色化分工”。
3. **全流程缺口集中在：** ①能力基准未跑（最大）；②编码/求解的操作性协议层薄；③写作的证据分配纪律与真实验证缺；④选择性重跑/敏感性编排与数学执行器缺；⑤往届卡选择没接进工作流；⑥状态多写+代码债；⑦认知负荷高。
4. **评审中纠正了三处过时结论**（见 §7）：METAMATH 文档说“往届索引为空、模型合同没投影成编码任务、论文计划没投影成章节写作任务”——**这三点当前代码里都已存在**，别按“缺失”来立项。

## 4. 分条详细建议

### R1 ｜先跑通“最小能力基准切片”（P0，最高杠杆）

**背景 / 问题。**
`CAPABILITY_BENCHMARK_PLAN.md` 明确：4 类任务族（优化/预测/评价/机制）× A0/A1/A2 预算档，共 12 次运行全部存在之前，只能写 `NOT RUN`。`BASELINE_BEFORE_VNEXT` / `VNEXT_EXECUTION_STATUS` 也确认：“没有任何外部论文项目、完整计算、独立验证、PDF 审查、比赛提交或 F1 冻结被真正跑过”。**这意味着当前所有“通过”都是回归/Schema 正确，不是能力证明。**

**建议。**
不要等 12 次都齐才动。**先做 1–2 次端到端真实运行**，把 `NOT RUN` 变成有 artifact 的证据，顺带把 R2/R3/R4/R5 在真实场景里检验一遍。仓库的往届隔离区已经有可用的真实题，优先就地取材：
- 优化族：`B226` 多波束测线布设（已在 `references/precedents/cumcm/index.json`）
- 预测族：`C228` 蔬菜定价补货（同上）
- 机制族：`2400996` 七鳃鳗性别比例（`mcm-icm/index.json`）

**落地步骤（以 B226 为例，在“独立项目根”执行，勿写进本仓库）。**
1. `harness init --project <ROOT> --competition cumcm --preset research`
2. `harness doctor --offline` → `harness status`，读 first blocker
3. 依次 `S0→M1→P1→P2→W1→W2→S1`，每关先读 `status` 的 first blocker 再修；人审点前跑 `prepare <STAGE>`
4. 用 `harness run -- python <真实模型代码>` 拿到真实 receipt；`harness freeze` 冻结结果
5. `harness review`（最好 `--fresh` + 独立 backend）产出 W2 review 证据
6. 把这次运行的 run_id、receipt、frozen_results、review、关键 hash 记录进一条**基准记录**（哪怕只有一条，也要把它从 `NOT RUN` 改成“已跑 1/12，附路径”）

**验收标准。**
- 存在一个真实 `run_id`：有成功 smoke receipt + 一个 selected full receipt + 一个冻结回执 + `status=frozen/claimable` 的 frozen_results + 一份 W2 review 报告。
- `CAPABILITY_BENCHMARK_PLAN` 的状态从 `NOT RUN` 更新为“已跑 N/12，逐条附 artifact 路径”。
- 关键数字能从 paper claim 反查到 evidence_registry → frozen_results → receipt/code → raw data。

**工作量。** 中（单题全流程约 1–2 个集中工作日，主要耗时在真实建模与求解本身）。

### R2 ｜给模型→代码交接补“操作性协议层” + 修 M1 阶段倒置（P0）

**背景 / 问题。**
投影本身已存在且已接线（**已核实**）：`harness solve --tasks` 会把 `model_contract` 投影成逐模型实现任务（方程/约束/带类型参数/作为 oracle 的验证义务/smoke 验收/步骤/升级路由），见 `scripts/views/implementation_tasks.py`，`harness.py:627,635,1076`。
但**缺的是“怎么写代码才稳”的操作性协议层**——同类（MathModelAgent `coder.py`、math-modeling-skill 编程手）有而本仓库没有：防泄漏、编码回退、大 CSV 协议、以及一份求解器鲁棒清单。另外 `implementation_tasks` 只说“实现什么”，不说“如何稳健地实现”。

**建议。**
1. **新增一份操作性编码协议 reference**，如 `references/research/coding_protocols.md`，内容直接吸收同类成熟经验：
   - **防泄漏：** 预测类特征用 `shift(1)`；只在训练集上 `fit`（标准化/编码器/插值同理）；时间序列严禁用未来数据。
   - **编码与读入回退：** 多编码尝试、`>1GB` CSV 分块/降类型协议、缺失值策略要登记。
   - **求解器鲁棒清单（9 点）：** log-sum-exp 防溢出；条件数 >1e7 → `pinv`/正则化；求解超时要有退化方案；多种子（固定 seed 并登记）；量纲/上下界合理性检查；`Big-M` 不能失真；对偶/间隙要报告；失败要留证据。
2. **把这份协议注入实现任务视图**：在 `implementation_tasks.py` 的任务渲染里，按 `problem_type`/`algorithm` 追加一节「本任务的鲁棒性检查清单」，让 coder 拿到的不只是方程，还有“这题容易踩的坑”。
3. **确认“阶段倒置”已修正，勿回退。** 评审核实：当前实现映射已是 **P2 后置工件**（`check_gates.py:790-811`，从 `03_SOLUTION_REPORT.md` 编译，`status=verified` 证明方程已实现），并不在 M1 前置。METAMATH 所说“enhanced M1 要求已验证实现映射”的阶段倒置在当前代码里**并不存在**（又一处过时结论）。这里要做的不是搬移，而是守住这个正确顺序，避免后续改动把实现映射校验提前回 M1。

**落地步骤。**
- 新建 `references/research/coding_protocols.md`（吸收同类、结合本仓库 16 张 failure 卡）。
- 在 `references/router.md` 的 research 行加链接；在 `implementation_tasks.py` 的 `render_markdown` 增加按 `problem_type` 选择清单片段的逻辑。
- 补一条回归测试，锁定“实现映射只在 P2 校验、M1 不强制”这一现状，防止未来改动把校验提前。

**验收标准。**
- `solve --tasks` 的输出里能看到按题型出现的鲁棒性清单。
- 一道真实题（可并入 R1）在编码阶段确实按清单规避了至少一个已知坑（如泄漏/溢出），并在 `03_SOLUTION_REPORT.md` 留痕。
- 回归测试锁定：M1 在无实现映射时通过，实现映射校验仅在 P2 生效（现状已如此，测试用于防回退）。

**工作量。** 中（协议文档 0.5 天 + 注入与关卡调整 0.5–1 天）。

### R3 ｜给写作交接补“证据分配纪律”，并用真实论文验证（P0/P1）

**背景 / 问题。**
写作投影也已存在且已接线（**已核实**）：`harness paper write <section>` 会把 `paper_plan` 编译成 `WRITING_SPINE.md`（中心论点、分节论证单元、跨问交接、确定性起草顺序、摘要证据预算）+ 每节 Writer Brief（claim/冻结值/已确立事实/不可声称边界），见 `scripts/views/writing_spine.py`，`harness.py:45,736-750`。
残留缺口：①没有 nature-shared 那种**结果证据分配纪律**（8 类结果→正文/图注/附录的去向 + “最短充分证据链”）；②没有在真实论文上验证过（METAMATH §9）；③`ENHANCEMENT_PROPOSAL` 痛点4 的“空洞化、符号漂移”没有被正面解决。

**建议。**
1. **引入结果分配纪律：** 在 `paper_plan` 或 `writing_spine` 投影里，为每个结果/论证单元标注分配去向类别（核心发现 / 对比 / 验证 / 机制推导 / 边界 / 边缘情形 / 方法选择 / 参数证据——正好可复用 `writing_spine._ROLE_PHASE` 的角色），并给出去向（正文 / 图注 / 附录）。配合“每加一处必须查是否可删一处”的防堆积规则。
2. **符号一致性扫描：** 利用已有 `check_consistency.py` / `terminology.forbidden_variants`，补一个“同一量两个名字/两个单位”的漂移检查（nature-polishing 的跨轮漂移检测思路）。
3. **用真实论文验证：** 在 R1 的那道题上，走完整写作链，产出论文，检查 Writer Brief 是否真的约束住了“不可声称边界”、摘要是否确实从 evidence registry 编译。

**落地步骤。**
- 在 `writing_spine.py` 的 section brief 增加 `evidence_allocation` 字段（类别 + 去向 + 字数预算），并在 `render_brief_markdown` 展示。
- 在 `check_consistency.py` 增加符号/单位漂移规则，或新增 `check_symbol_drift.py` 并挂进确定性 QA。
- 结合 R1 跑一次真实写作，把“空洞化/符号漂移”作为验收观察点。

**验收标准。**
- 每节 Brief 能看到“本节结果分配去向表”。
- 真实论文里，摘要的每个数字都能在 evidence registry 找到对应 `result_id`；无未登记符号漂移。
- 至少一次“新增触发删除检查”的留痕。

**工作量。** 中（分配字段+渲染 0.5–1 天；符号漂移检查 0.5 天；真实验证并入 R1）。

### R4 ｜把往届 / pattern-card 选择接进工作流（P1）

**背景 / 问题。**
资产已经齐了（**已核实**）：`cumcm/index.json` 6 篇、`mcm-icm/index.json` 4 篇，全部 SHA-256 校验、`extraction_status=extracted`；`select_reference_cards.py` 有单测。但它**不是 `harness` 子命令、也不是任何 Gate 的一步**——赛时得靠人记得手动跑。另有上游新鲜度复核（GAP-16）未做。

1. **加一个 `harness precedents` 子命令族**：`harness precedents select --competition cumcm --problem-family optimization [--role ...]`，底层调 `select_reference_cards.select_cards`，输出命中的 pattern-cards / figure-cards 清单 + 阅读顺序。

3. **做一次上游新鲜度复核（GAP-16）**：确认 `upstream_refs/` 快照是否落后于上游，更新或标注 `last_reviewed`。

**落地步骤。**

**验收标准。**

- 一次真实 research 阶段（并入 R1）确实消费了至少一张机制卡，并记录来源。

**工作量。** 小（包一层 CLI + 提示 0.5 天；新鲜度复核 0.5 天）。

### R5 ｜选择性重跑 / 敏感性编排 + 先做单位/量纲执行器（P1）

**背景 / 问题。**
验证的**工件体系很强**（`validation_obligations`、profiles、`sensitivity_experiment`、`oos_artifact`、`extremum_certificate`、`failure_evidence`），但两块执行缺：①GAP-08“选择性重跑/敏感性编排缺失”——改一个参数后，没有机制自动判断哪些 receipt/结果受影响、只重跑受影响的部分；②GAP-07 / STATUS 的 M0–M4 **数学执行器缺失**（代数/单位/索引/量纲/符号等价），高风险数学仍完全依赖 W2 人工。

**建议。**
1. **单位/量纲执行器先行**（性价比最高）：在 `model_contract` 的 `parameter_plan` 已有 `unit` 字段（**已核实**，见 `implementation_tasks.py` 对 `unit` 的投影）。新增一个确定性检查器 `scripts/qa/check_units.py`：校验方程两侧量纲一致、参数单位在整链一致、结果单位与 `acceptance.unit` 一致。挂进确定性 QA 与 M1/P2。
2. **选择性重跑编排：** 基于 `artifact_dag.json` 的依赖关系，给定“某输入/参数变更”，计算下游受影响的 receipt 与冻结产物，列出“需要重跑的最小集合”，并让下游 Gate 置为 pending。先做“只生成重跑计划 + 失效标记”，不自动执行。
3. **敏感性编排：** 把 `sensitivity_experiment` 从“单个工件”升级为“一次 sweep 生成多个工件并汇总”的编排（可复用 `check_sensitivity_experiment.py`）。

**落地步骤。**
- 新增 `check_units.py` + schema 里补 `dimension` 约束字段；在 `run_deterministic_qa.py` 的 flag 矩阵里接入。
- 在 `qa/check_artifact_dag.py` 或新 `qa/plan_selective_rerun.py` 里实现“影响集合”计算，输出到 `.harness/views/RERUN_PLAN.md`（投影，不是命令执行）。
- 回归测试覆盖：量纲不一致必须被拦下；改一个冻结输入后下游显示 pending。

**验收标准。**
- 一个故意写错量纲的模型合同被 `check_units` 拦下。
- 给定一次参数变更，能输出正确的最小重跑集合，且相关下游 Gate 变 pending。

**工作量。** 中（单位执行器 1 天；重跑编排 1–1.5 天；敏感性编排 1 天，可分期）。

### R6 ｜还状态 / 代码债（P1）

**背景 / 问题。**
`STATE_SIMPLIFICATION_AUDIT` 指出四个事实域 ownership 未收口：Competition Profile 双源且 ontology 不兼容、Command State 三写、artifact identity/digest 多写、72 种理论 profile 组合；且回归基线非全绿（2 errors；full-discovery 状态“unknown，不是 pass”）。评审也确认了巨型函数：`check_gates.py main()` 约 1100 行（双系统）、`v2_gate_runtime._v2_gate` 约 460 行 if/elif、v1/v2 写手重复（`run_and_record.py`、`freeze_submission.py` 把 F1 逻辑写了两遍）。

**建议（按“先绿、再收口、再拆分”顺序）。**
1. **先把回归跑绿：** 复现并修掉那 2 个 error（缺 numpy / UTF-8 解码），让 `python -m unittest discover -s tests` 成为可信基线；把 full-discovery 跑出真实结果并记录。
2. **收口 Command State 三写：** 让“命令状态”只由 receipt 产生，manifest/index 只做派生；清理 `--command-receipt` 可选但未兑现的口径。
3. **对齐 Competition Profile 双源：** 统一 seed→standalone 的 ontology，消除两套字段并存。
4. **拆巨型函数（放到收口之后，避免边拆边改语义）：** 把 `check_gates.py` 的 v2 与 legacy v1 拆成独立模块；把 `_v2_gate` 的 per-gate 分支抽成每关一个纯函数（输入=事实，输出=判定）。
5. **去 v1 重复：** 在确认迁移完成后，删除 `_run_v1` / v1 F1 的重复实现，只留迁移期兼容。

**落地步骤。** 每一步都配回归测试；拆分用“先加新模块并双跑对拍 → 切流 → 删旧”的方式，避免一次性大改。

**验收标准。**
- `unittest discover` 全绿且结果被如实记录（不是沿用历史 305/305 口径）。
- 命令状态只有一个写者；profile 只有一套字段。
- `check_gates.py` / `_v2_gate` 无 >300 行的单函数；v1 重复实现删除。

**工作量。** 中/大（跑绿 0.5 天；收口 2–3 天；拆分 2–3 天，可分多个 PR）。

### R7 ｜渲染级图 QA + Figure Reference Cards（P2）

**背景 / 问题。**
图的路由很强（`figure_contract`、`tool_router`、`pptx_router`、drawio、illustration），但缺：①**渲染级**的碰撞/对齐审查（nature-figure 有、带阻塞 exit code）；②Figure Reference Card 视觉经验库（METAMATH §3.2）；③GAP-05（`\includegraphics` 与 `rendered_paths` 无绑定，曾出现位图冒名）与 GAP-13（caption 与实文比对）。

**建议。**
1. **渲染级图 QA：** 对导出的最终图做机器检查——面板对齐容差、元素碰撞/越界、字号下限、纸面尺寸；失败给阻塞 exit code（区分“需修”与“不可审”）。
2. **Figure Reference Cards：** 把已抽出的往届图（`references/precedents/figure-cards/` 已有 6 张 + schema）扩成一个“按语义类型索引”的视觉经验库，并与 `pptx_router` 的候选选择联动。
3. **闭合 GAP-05 / GAP-13：** 让论文里每个 `\includegraphics` 绑定到一个已登记的 `rendered_path`+hash；caption 与正文数字做一致性比对。

**验收标准。** 一张故意越界/碰撞的图被拦下；论文中每张图片可反查到登记产物；caption 数字与正文一致。
**工作量。** 中（渲染 QA 1.5 天；卡片库 1 天；两个 GAP 各 0.5 天）。

### R8 ｜降认知负荷：契约模板化 / 派生化（P2）

**背景 / 问题。**
约 30 个 schema、15+ 需手工填写的 JSON 契约；`ENHANCEMENT_PROPOSAL` 痛点1 “为了填契约而填契约”。完整性被优化到了，代价是赛时的填写负担与交接摩擦。

**建议。**
1. **能派生的就别手填：** 优先从作者面 `00_*.md` 的 YAML block 编译（机制已有），把手工 JSON 降到“每个 Gate 真正消费的最小集”。
2. **提供脚手架模板：** `harness init` 后按 preset 生成“带注释的最小契约样例”，而不是一堆空 schema。
3. **按 Gate 暴露契约：** `status` / `prepare` 只显示当前关卡需要填的字段，其它折叠。
4. **做一次“契约消费审计”：** 对每个 schema 标注“哪个 Gate/命令消费它”，删掉无消费者的字段（与 R9 呼应）。

**验收标准。** 一道新题从 `init` 到 M1，需要手工填写的字段数显著下降；每个契约字段都能指到至少一个消费者。
**工作量。** 中（审计 1 天 + 模板/派生改造 2 天，可渐进）。

### R9 ｜建立“文档↔代码对账”的 living-architecture 机制（P2，评审新发现）

**背景 / 问题。**
本次评审在一篇标注为“最新（2026-08-28）”的设计文档里发现**三处与代码不符**的结论（见 §7）：往届索引被说成空、两个投影被说成不存在——而它们其实都已实现并接线。这说明设计文档没有跟代码对账，容易误导后续立项（把“已有”当“缺失”重复造）。

**建议。**
1. **给关键设计文档加“可核验断言”：** 像 `harness doctor` 一样，写一个轻量检查（如 `scripts/qa/check_doc_claims.py` 或并进 `doctor`），把几条高频被引用的文档结论转成可检查项（如“索引非空”“`solve --tasks` 存在”“`paper write` 存在”），失配就报警。
2. **文档加 `verified_against` 元信息：** 每篇设计文档头部记录“对账到的 commit/日期”，超过阈值（如一次大版本）未对账就标记 `stale`。
3. **把“对账”纳入发布流程：** 发版/交付前跑一次对账，结果如实记录。

**验收标准。** 重跑对账时，之前那三处失真能被自动标出；新文档默认带 `verified_against`。
**工作量。** 小（0.5–1 天）。

### R10 ｜可分发包（P3，勿阻塞主线）

**背景。** README 承认尚无独立分发 wheel，只能 editable checkout；这阻碍复用/分发。
**建议。** 在主线（R1–R5）验证后再做：把 schemas / references / assets / 模板纳入打包完整性校验，产出一个可 `pip install` 且通过资源完整性检查的 wheel。**不要**用一次 `pip install .` 成功来冒充资源完整性验证（这是 README 自己强调的边界）。
**工作量。** 中。优先级最低，除非有明确分发需求。

## 6. 明确**不建议**做的事（护栏）

这些是评审和项目自身经验共同指向的“别踩的坑”：

1. **不要再加新的 Gate 或新的 Agent 角色**来“看起来更完整”。`HARNESS_INTEGRATION_ANALYSIS` 的判断仍然成立：Gate 是状态转换，不是 Agent 数量；先把可追溯链路跑通再谈扩展。
2. **不要用回归测试通过 / Schema 校验通过来宣称能力。** 能力必须由 R1 的真实运行背书；没跑就写“未跑”。
3. **不要手写或伪造** Gate PASS、receipt、hash、review 结论、frozen 结果；改不可变产物要走“新版本 + 下游失效”。
4. **不要为了降认知负荷而削弱不可绕过项**（Contest Safety、人审、独立验证、结果冻结、提交不可变）——这些是 `SAFE_INVARIANTS`。
5. **不要把往届论文原文当当前证据**；只用抽出的机制卡，且遵守 `precedent_policy` 的“≤2 篇同赛同题、只校准不抄袭”。
