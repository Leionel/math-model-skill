# CUMCM Empirical Presentation Prior

这是一份可选的经验性写作先验，来源于对 `yuanchen-home/cumcm-step-review` 及其引用的公开竞赛写作资料的机制提炼。它不是中国数学建模竞赛官方规则，也不是必须逐条执行的模板。当前题目、当届 profile、用户提供的完整模板和 `paper_plan` 优先级更高。

## Observed：常见的有效做法

- 评委先看题意是否被正确转译，再看模型是否真的回答每一问，最后才看细节和修辞。
- 逐问呈现通常更清楚：问题输出/目标 → 关键假设与符号 → 模型与求解 → 结果 → 验证 → 解释与边界。
- 摘要需要二次事实核查；模型名称、决定性数字、单位、比较关系和验证口径容易在改写中漂移。
- 图表最有用的不是数量，而是是否让读者更快判断一个明确主张；总览图、模型框架图和数据证据图承担的论证任务不同。
- 图表在论文最终尺寸下常会出现字体、图例、裁切和颜色语义问题；导出成功不等于可读。

这些观察只产生审阅方向，不能自动推出“所有论文都必须使用某种模型、某种图或某种段落句式”。

## Recommended：适合作为软性审阅项

### 写作顺序

研究过程可以是：题意 → 调研与候选比较 → 模型 → 代码 → 结果 → 验证；论文呈现可以是：问题重述 → 分析与假设 → 符号 → 模型 → 求解 → 结果 → 验证 → 讨论。摘要最后写，但其答案字段在 W1 先登记。

### 逐问论证

每问至少让读者找到四件事：实际要输出什么、采用的模型为何适配、结果是什么、结果依赖什么边界。可用 CEEL（claim/evidence/explanation/limitation）组织结果段，但不强迫每段使用四个固定标题。

### 图表审阅

画图前登记 `argument_intent`、`data_shape`、`sample_regime` 和 `uncertainty_semantics`。先写一句图的 primary claim，再在候选显示中选择最能支撑该 claim 的图型；不要因为“还缺一张图”而填配额。概念总览图保留 draw.io 等可编辑源，数据图保留数据和生成脚本；二者都要在最终论文尺寸下复核。

### 评委速扫

使用 issue-only `judge_scan` 询问：30 秒能否找到方法和答案，决定性数字是否可见，验证是否可发现，图后 1–2 个段落是否解释了主张。它只列待人工检查的问题，不输出总分，也不替代数学正确性审阅。

## Not Mandatory：明确不继承为 Harness 硬规则

- 固定摘要句式、固定“先介绍什么再介绍什么”的模板化段落；
- 固定参考文献数量、固定模型评价章节或固定摘要结果数量；
- 固定图表数量、每问固定图数、候选模型固定数量或某种图型配额；
- 把“非线性就用 LSTM”“小样本就用 GM(1,1)”之类经验快捷映射当成模型选型；
- 固定使用 ±10%/±20% 敏感性区间，或把“可能”一词一律视为不合格；
- 复制上游仓库中的优秀摘要、整段语料或第三方模块。

## 使用方式

本先验默认只产生 `RECOMMENDED`、`MISSING` 或人工 issue。只有当当前比赛 profile、用户模板或项目合同明确要求时，才可以把某项升级为正式 Gate，并应在 manifest 中留下 profile 依据。其目的，是提高论文的可读性和审阅效率，而不是把不同赛题压成同一篇模板文。
