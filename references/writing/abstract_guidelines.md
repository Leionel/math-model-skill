# Abstract Guidelines

摘要是一篇可独立判断质量的微型论文，不是背景介绍或工作计划。它应让评审快速看清：解决了什么、如何解决、得到什么、结论在什么边界内成立。

## Evidence Gate

摘要中的关键数字必须列入 `paper_plan.abstract_results[]`，说明选择原因、关联 claim 与词数预算，并能沿 `evidence_registry → frozen_results → code/input` 回溯。不要从聊天、草稿或截图复制数字。

- 使用冻结的 `display_value`、单位和统计口径，不重新舍入。
- 没有注册的数字不得进入摘要；年份、题号等非结果数字由一致性检查单独解释。
- “最优、显著、稳健、提升”必须有相应比较、统计或敏感性 evidence。
- 正文没做的检验、推广或创新不要写进摘要。

## 推荐结构

段落数量跟随子问题和版面，不固定为四段。

1. **一句总起**：直接说明问题、总体方法和交付目标，不铺长背景。
2. **按子问题展开**：每个子问题尽量包含“模型/方法—关键处理—核心结果—边界”；有递进关系时明确写出。
3. **一句收束**：只总结已完成的验证、稳定性或适用范围。
4. **关键词**：3–5 个具体领域、模型或算法名，避免“数学建模、优化、算法”等泛词。

## 写作规则

- 使用完成态：建立、采用、得到、验证；避免“将要、计划、接下来”。
- 用事实替代自评：“样本外误差为 4.2%”优于“预测十分准确”。
- 只保留决定结论的少量结果；次要参数放正文或附录。
- 单位、有效数字、符号和术语与正文、图表一致。
- 通常不放公式和文献引用；如果当届模板另有要求，以 Competition Profile 为准。
- 不引用内部工程文件名，也不写“详见附件”代替结论。

## 常见失败

- 背景占据开头，直到末尾仍不知道模型和结果；
- 只有“建立模型、结果有效”，没有具体证据；
- 每问机械套同一句式，读不出重点或递进；
- 堆砌“首次、重大、鲁棒、先进”等无证据形容词；
- 数字缺单位、重新舍入，或与正文/结论漂移；
- 把图表数量、模型复杂度或算法名称当作贡献本身。

## 执行顺序

1. 正文主张和结果基本稳定后再写摘要。
2. 从 `paper_plan` 选择覆盖关键 requirement 的少量冻结结果。
3. 先写“方法—结果—边界”，再删背景和自评。
4. 运行 Consistency Sweep 与 deterministic QA。
5. 由 W2 人工检查摘要是否独立可读、是否夸大证据。

## 最终检查

- [ ] 首句是否进入问题和方法，而非泛泛背景？
- [ ] 每个必要子问题是否有明确回答？
- [ ] 所有关键数字是否来自 `abstract_results[]`，单位与精度一致，且确实是决定结论的高优先级结果？
- [ ] 是否说明关键结果的比较口径或适用边界？
- [ ] 是否删除未来时、空泛评价和未完成工作？
- [ ] 是否符合当届页数、语言和摘要页要求？
